# 06-消息加解密技术介绍

> 适用范围：`github.com/jcbowen/wego/crypto` 与 `github.com/jcbowen/wego/message`，
> 微信开放平台第三方平台 / 公众号 / 小程序的消息加解密。

## 一、加解密原理（微信官方规范）

### 加密流程

1. 生成 16 字节随机字符串（random）
2. 构造明文：`random(16B) + msg_len(4B, 网络字节序) + msg + appid`
3. AES-256-CBC 加密（以 aesKey 前 16 字节作为 IV），PKCS7 填充
4. Base64 编码加密结果，得到 `msg_encrypt`
5. 生成签名：`msg_signature = sha1(sort(token, timestamp, nonce, msg_encrypt))`

### 解密流程

1. 校验时间戳（防重放，超出容忍窗口判定为无效请求）
2. 验证消息签名（`msg_signature` 参数）
3. Base64 解码 + AES-256-CBC 解密 + PKCS7 去填充
4. 解析消息结构，**校验明文尾部 appid** 与配置一致
5. 当前 EncodingAESKey 解密失败时，降级尝试上一次的 EncodingAESKey（密钥轮换过渡期，官方要求）

## 二、本库实现

### 1. 底层 AES 函数（`crypto` 包）

| 函数 | 说明 |
|---|---|
| `crypto.DecodeAESKey` | 43 位 EncodingAESKey（尾部补一个 `=` 后 Base64 解码）→ 32 字节 AES 密钥 |
| `crypto.EncryptMsg(plainText, appID, aesKey)` | 纯 AES 层加密，返回 Base64 密文 |
| `crypto.DecryptMsg(encryptedMsg, aesKey)` | 纯 AES 层解密，含 PKCS7 去填充与消息结构/appid 校验 |
| `crypto.DecryptMiniProgramData(sessionKey, encryptedData, iv, result)` | 小程序客户端数据解密（AES-128-CBC，详见小程序模块说明） |

### 2. 完整加解密器 `crypto.WXBizMsgCrypt`

封装签名校验、时间戳容差、密钥轮换降级的完整实现：

```go
// 基础构造（无存储，密钥轮换过渡期无法解密旧密钥消息）
c := crypto.NewWXBizMsgCrypt(token, encodingAESKey, appID)

// 推荐构造：注入 TokenStorage，支持加载/持久化密钥轮换过渡期的上一次密钥
c, err := crypto.NewWXBizMsgCryptWithStorage(token, encodingAESKey, appID, store)
```

| 方法 | 说明 |
|---|---|
| `VerifyURL(msgSignature, timestamp, nonce, echostr)` | 回调 URL 有效性与 echostr 解密（首次配置服务器时用） |
| `VerifySignature(...)` / `GenerateSignature(...)` | 签名校验 / 按官方参数顺序生成签名 |
| `DecryptMsg(...)` | 解密消息（验签 + 时间戳容差 + 密钥降级），返回明文 |
| `DecryptMsgWithKey(...)` | 同上，额外返回 `usedAesKey`（实际解密成功所用的 EncodingAESKey） |
| `EncryptMsg(replyMsg, timestamp, nonce)` | 加密回包，返回 `(密文, 签名)` |
| `EncryptMsgWithKey(replyMsg, timestamp, nonce, key)` | **用指定密钥**加密回包（密钥轮换过渡期用） |
| `SetPrevEncodingAESKey(prevKey)` | 手动设置上一次密钥 |

**密钥轮换（官方要求）**：收到 `encoding_aes_key_changed` 事件后，用新密钥加密的消息需用新密钥解，
用旧密钥加密的在途消息需用旧密钥解。官方规则是——**用哪个 AESKey 解密成功，就用该 AESKey 加密回包**：

```go
plainText, usedAesKey, err := c.DecryptMsgWithKey(msgSignature, timestamp, nonce, encryptedMsg)
if err != nil {
    return err // 当前密钥与上一次密钥均无法解密
}

// ...业务处理 plainText...

// 回包：解密成功用的是哪个密钥，回包就用哪个（签名始终使用当前 Token，Token 不随密钥轮换变化）
var encrypted, signature string
if usedAesKey != c.EncodingAESKey {
    encrypted, signature, err = c.EncryptMsgWithKey(replyXML, timestamp, nonce, usedAesKey)
} else {
    encrypted, signature, err = c.EncryptMsg(replyXML, timestamp, nonce)
}
```

> 时间戳容差：`DecryptMsg` / `VerifyURL` 内部会校验时间戳，超出容忍窗口判定为无效请求（防重放）；
> timestamp 为空或非数字时保守跳过校验。签名算法参数顺序固定为 `token, timestamp, nonce, msg_encrypt` 排序后 SHA1。

### 3. 消息处理器 `message.SecureMessageProcessor`

面向回调服务的更高层封装：一条调用完成「时间戳校验 → 取加解密实例 → 验签 → 解密 → 消息解析 → 回包加密」全流程：

```go
// 第三方平台多授权方场景：注入配置提供者（按 authorizerAppID 返回 token 与 EncodingAESKey）
p := message.NewSecureMessageProcessor(
    message.WithCryptoConfigProvider(message.CryptoConfigProviderFunc(
        func(authorizerAppID string) (string, string, error) {
            return loadTokenAndAESKeyFromDB(authorizerAppID) // 业务侧实现
        })),
    // 可选：注入存储后可加载密钥轮换过渡期的上一次密钥；未注入时 PrevKey 恒为空，
    // 轮换过渡期用旧密钥加密的消息将无法解密
    message.WithTokenStorage(store),
)

// 单授权方 / 自建公众号场景：直接指定默认配置
p = message.NewSecureMessageProcessor(
    message.WithDefaultCryptoConfig(token, encodingAESKey),
    message.WithTokenStorage(store),
)

// 处理加密回调：返回加密后的回包 XML（或 "success"）
reply, err := p.ProcessSecureMessage(authorizerAppID, msgSignature, timestamp, nonce, encryptedMsg)
```

内部行为要点：

- 按授权方 AppID 缓存 `WXBizMsgCrypt` 实例（`CryptoCache`），避免重复构造；配置变更可调 `ClearCryptoCache(authorizerAppID)` 清除
- 解密统一走 `DecryptMsgWithKey`，回包自动遵守「用哪个 key 解密成功就用哪个 key 加密」
- 回复 `"success"` 时直接透传（官方要求的确认应答）
- 支持 `VerifyURL` 处理 URL 有效性验证

## 三、故障排除

| 现象 | 排查方向 |
|---|---|
| 消息签名验证失败 | Token 配置是否与微信后台一致；签名参数顺序是否为 token/timestamp/nonce/msg_encrypt |
| 解密失败（当前与上一次密钥均无法解密） | EncodingAESKey 是否为 43 位且与后台一致；是否未注入 TokenStorage 导致轮换过渡期旧密钥不可用 |
| 时间戳验证失败 | 服务器时间同步（NTP）；重放或长时间积压的消息 |
| AppID 不匹配 | 密文尾部 appid 与实例配置的 AppID 不一致，检查是否用错授权方配置 |
